## 2. The login failures on 2026-10-04

Alpha's security feed showed six `login — login on /auth/login — failure`
entries between 00:19:42 and 00:25:42 (the audit store writes UTC, so 01:19 to
01:25 UK time).

**What they are.** Each is one `POST /auth/login` that `api/auth.py` rejected
as `invalid_credentials`: a wrong username or a wrong password. Nothing was
accepted. None was a 2FA or rate-limit event; those log as `2fa-required` and
`blocked`.

**Who.** Not knowable from a cloud container: the username tried and the IP are
in Laptop41's databases. The pattern (six attempts over six minutes, 10 s to
3.5 min apart) is a person retyping, not a scripted attack, and it ended just
before V started this session. The first thing to check is whether it was V.
To see the account and address, as owner:

- `GET /auth/security-events`: owner only; username, IP and user agent for each `login-failed`.
- `GET /audit/events?action=login&status=failure&since_minutes=1440`: needs access level 6 or above; actor and IP.

If the IP is not V's own and the username is real, change that password and
enable TOTP for it.

**What changed (Alpha #36, on `alpha-full`).**

- An unknown username now costs the same password hash as a known one, so
  response time no longer says which usernames exist.
- Failed sign-ins are capped per account across all addresses: 30 per 15
  minutes (`LOGIN_ACCOUNT_FAILURE_LIMIT`, `LOGIN_ACCOUNT_FAILURE_WINDOW_SECONDS`).
  Only failures count. The per-address limit (10/min) was already there.
- The feed now reads `login as <username> on /auth/login — failure`, so the
  next one says which account it was for.

It is merged on `alpha-full` only. Laptop41 runs a local working copy, so it
has none of this until that copy is updated (§3).
